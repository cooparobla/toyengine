# toyengine/cloth (`toy::cloth`)

Clothing on animated rigs: a garment mesh simulated as XPBD cloth, with per-vertex painted
channels deciding how much each vertex follows the skinning and how much it swings free.

For a procedural **grid** sheet pinned to rigid bodies (a flag, a dust cover) use physxcoopa's
`Cloth` + `ClothRenderer` instead — see
[`physxcoopa/cloth/README.md`](../../libs/physxcoopa/physxcoopa/cloth/README.md), which also
documents the solver this directory drives.

## The pieces

| | |
|---|---|
| [`character_cloth.h`](character_cloth.h) | The `CharacterCloth` component: authoring data only (tunables, `bone_colliders`), keyed state lives in the system |
| [`cloth_mesh_system.h`](cloth_mesh_system.h) | `ClothMeshSystem`, update order **346** — builds, skins, solves, and deforms |
| `physxcoopa/cloth/cloth_mesh_builder.h` | Arbitrary-mesh cloth: edge/apex constraints, greedy-coloured disjoint batches, area masses |
| `render/passes/cloth_deform_pass.h` + `assets/shaders/cloth_deform.comp` | The GPU deform dispatch |

## Authoring

A garment is three components on one object: a `MeshRenderer` with **no `mesh_path`** (material
and draw), a `SkinnedMeshRenderer` (mesh and rig), and `CharacterCloth`.

```yaml
- type: MeshRenderer
  material: { albedo: {r: 0.46, g: 0.10, b: 0.16}, cull_backfaces: false }
- type: SkinnedMeshRenderer
  mesh_path: animation/jacket
- type: CharacterCloth
  mass_per_area: 0.25
  # auto_colliders is ON by default: every DRAWN part riding the rig gets a capsule fitted
  # around it, so the arms and legs push the garment out as they swing. An entry below
  # CORRECTS one bone (`radius: 0` drops it); most garments need none.
  collider_scale: 1.05
```

**Collide with the body you can SEE, not with a list and not with the skeleton.** A garment that
only meets the bones someone remembered to type is a garment an elbow goes through, so
`auto_colliders` is on by default. What it fits them to matters just as much: a capsule derived
from a bone's LENGTH is a guess about a body it has never seen, and on the demo mannequin it was
wrong by 3-8 cm on the hands, the chest and the pelvis -- cloth held off a body nobody is looking
at while the drawn one hung through the fabric, with every penetration test passing. So each
object riding the rig on a `BoneAttachment` has a capsule fitted around its own mesh instead,
exact for the elliptical-section parts a character is built from. `auto_bone_capsule()`'s
bone-length rule remains the fallback for a bone nothing is drawn on -- a skinned body mesh, or a
bone that only carries other bones.

Write a `bone_colliders` entry only for a part the fit cannot describe (a box-section shape, whose
corners it leaves uncovered by up to 41% of its radius) or to drop one. An entry replaces every
collider on its bone.

Which vertices simulate is **painted on the mesh**, not set here — the mesh YAML's `cloth:` key,
authored by the editor's Cloth Paint mode (the component's inspector has the button):

| Channel | Means |
|---|---|
| `max_distance` | metres the vertex may leave its skinned position. **0 = fully skin-driven** (the collar stitched to the shoulders); larger = looser |
| `backstop_distance` / `backstop_radius` | a sphere tucked behind the skinned surface the fabric is pushed out of — a cheap second line behind the bone colliders, following the garment's own skinned shape |
| `anim_drive` | 0..1 gain on the spring pulling simulation back toward the skinned pose |

Channels are per **raw** vertex (parallel to `vertices:`), like `weights:`. They are deliberately
NOT a vertex group: `SkinnedMeshSource` derives its bone palette from *every* group, so a cloth
group would eat one of the four influence slots and resolve to bone −1.

Worked example: `assets/scenes/animation/character_cloth_demo`, mesh generated by
`tools/gen_jacket_mesh.py` — a jacket **fitted** from collar to waist (painted `max_distance: 0`,
so it rides the skinning exactly) **flaring into a loose skirt** below the hips that the legs push
around as they swing. That split is what the channels are for, and it is a far better test of a
garment than a sheet: a fitted panel reveals seam popping, and a free hem reveals collision.

**Start the garment OUTSIDE the body.** The generator's profile narrows at the waist and flares
only below the hands, because the mannequin's forearms hang at x ±0.21 with their inner edge at
~0.163 m. A ring wider than that between z 0.82 and 1.14 is authored *inside* the arms, and a
garment that starts inside the body is one the solver spends every frame pushing out while the
`max_distance` leash pulls it back — which looks like jitter in the cloth and is really a modelling
error.

## Why order 346

A garment constrained to **this frame's** skinned pose cannot solve inside the physics step
(order 100) — the rig pose is written at 300–340 (SkeletalAnimation, IK, Ragdoll, RigPose). At
346, after `BoneAttachment` (345) and before `TransformResolve` (350), the pose is final, and the
physics world finished stepping at 100, so its broadphase holds the poses this frame draws
(`PhysicsWorld::gather_cloth_colliders()` is read-only and safe between steps).

That buys **zero frames of lag** between animation and cloth, which is what separates clothing
from Unity's one-frame-stale cloth. The cost: these cloths are owned by the system rather than by
`PhysicsWorld`, so they are outside `world_state_hash()`. Determinism is covered instead by the
solver's serial-vs-parallel bit-identity tests (`cloth_solver_test.cpp`). Coupling stays one-way:
nothing downstream of physics reads the result.

## The frame

```text
346  ClothMeshSystem::execute
       reconcile entries by state_key (rebuild only on a topology-hash change)
       skin this frame's targets   (SkinnedMeshRenderer::updated_skin_matrices, JobEngine)
       gather colliders            (world broadphase + bone colliders posed from the rig)
       solve                       (XPBD; JobDispatch parallel past 2048 particles)
       post-solve                  (object-space positions, area-weighted normals, bounds)
---- Engine::upload_dynamic_meshes_ ----
       GPU: upload the welded sim buffer, enqueue one ClothDeformPass job, mark_gpu_written
       CPU: skin, blend by the baked per-vertex weight, update_vertices
```

The simulation runs on the mesh's **welded** vertices (`SkinnedMeshSource::source_positions`;
`source_vertex` maps each unwelded render corner back to one), so no positional welding is ever
guessed at here.

## Traps

- **State is keyed by owner path, never by a `Component*`.** The editor destroys and recreates a
  component on every inspector keystroke. The rebuild gate hashes topology-affecting inputs only,
  so dragging a tunable never resets the simulation.
- **GPU deform rides `render.skinning`.** It is skinning with a blend on top; a device without
  compute, or `skinning: cpu`, takes the CPU blend. `preserve_volume` also falls back to the CPU
  (the kernel is linear-blend only). Both paths must agree — `character_cloth_render_test.cpp`
  asserts it vertex for vertex and pixel for pixel.
- **No cloth paint, no simulation.** A mesh without a valid `cloth:` key leaves the component
  inert with one logged warning; the garment just draws as plain skinning.
- **Bone colliders assume near-uniform bone scale** — the shape's metres are authored, not scaled
  by the bone.
- **Skin-driven vertices skip collision**, as anchored cloth particles always have. A collar
  painted `max_distance: 0` sits exactly where the skinning puts it, inside the torso capsule
  if that is where it was modelled — correct, and why the demo's penetration test measures
  only simulated vertices.
